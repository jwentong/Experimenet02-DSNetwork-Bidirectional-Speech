# 实验二 实验报告

## 一、原理与手算
T 交换按控制表把输入时隙重排到输出时隙，控制方向为输出→输入。
单 T 手算：输入 TS1=11、TS3=33，控制表 {1:3, 3:1}，输出应为 TS1=33、TS3=11。
单 S 手算：TS3 时输出链路 0 选输入链路 1，取链路 1 的 TS3，不换时隙。
C1 双向控制表：A=(0,1)、B=(1,5)，写 T0[5]=1、S[(1,5)]=0、T1[1]=5、S[(0,1)]=1。
C2 双向控制表：C=(0,2)、D=(1,6)，写 T0[6]=2、S[(1,6)]=0、T1[2]=6、S[(0,2)]=1。

帧字节计算：sample_frame 公式下，帧 0 的 A=(0+3+0)mod256=3，B=(101+15+0)mod256=116。
预期输出帧 1 的 B 位置=3、A 位置=116。

## 二、结果分析
运行仿真生成了 transfer_check.json，共计 16 条传送记录（2连接 × 2方向 × 4帧）。
数据表明，16次传输的 mismatch（错配）为 0，每条记录中 available_frame_id = k+1，符合一帧延迟的约定。
C1 与 C2 的四条方向同时工作，control_tables.json 中的 T/S 表项与上述手算完全一致。

## 三、反例与验证
1. 内部 T 冲突：C1 存在时请求 (0,2)-(0,5)，需要 T0[5]，与 C1 撞车，connect_pair 返回 False 且原表不变，C1 继续传送。
2. 释放隔离：释放 C1 后，C2 仍正常保持。重复释放 C1 返回 False，释放后的资源可重新建立连接。
3. 自拟测试 `test_my_case.py` 验证了释放、重复释放拦截、资源重用。

## 四、局限
帧缓存是本实验约定，不代表所有真实T接线器延迟；TS16保留也不是所有E1配置统一要求。
本实验实现不做多级路径搜索与自动绕路。
